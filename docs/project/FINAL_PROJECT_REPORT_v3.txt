1 Introduction and Business Problem

What if a project plan could be built straight from the meeting where the project was born, and stay correct when the project changes?

In short: project plans are built by hand from scattered notes and go stale quickly; NirnAIn turns notes into optimized, versioned plans.

1.1 The Problem

Projects start in meetings, but plans start in spreadsheets. A project manager (PM) must turn notes into a charter, a scope, a work breakdown structure (WBS), a staffing plan and a schedule. The Project Management Institute treats planning, scope and change as core performance domains [1]. Yet the translation is still manual.

Four problems follow:

• Manual planning. Requirements and risks are buried in free text. Errors flow into the WBS and the schedule.
• Resource conflicts. Schedules assume full-time people. Part-time allocations, skill levels and other projects are ignored.
• Opaque plans. When budget, deadline and people cannot all fit, tools rarely say why or what the options cost.
• Uncontrolled change. Mid-project changes are absorbed silently. Nobody can say which plan was approved and why.

The stakes are real. Flyvbjerg and Budzier [2] describe an enterprise system migration budgeted at under $5 million that ended in a $192.5 million charge against earnings.

1.3 Solution Overview

In short: seven planning steps, one optimizer, one AI layer with a rule-based fallback, all on a secure web stack.

Figure 1 shows the workflow. The PM creates a project, runs AI intake on notes, reviews the scope, builds the WBS and sets constraints. The optimizer then produces Plan v1. Mid-project changes loop back through re-planning to Plan v2, v3 and so on.

Figure 1. The NirnAIn workflow: seven steps, the re-planning loop and the dashboard.

    +-----------+   +-----------+   +-----------+   +-----------+   +-------------+   +------------+   +-------------+
    | 1 Create  |-->| 2 AI      |-->| 3 Scope   |-->| 4 WBS     |-->| 5           |-->| 6 Optimize |-->| 7 Changes   |
    | project   |   | intake    |   | review    |   | builder   |   | Constraints |   | Plan vN    |   | & versions  |
    +-----------+   +-----------+   +-----------+   +-----------+   +-------------+   +------------+   +-------------+

The stack is shown in Figure 2. A React [3] web app calls a Python FastAPI [4] service. Each query runs in PostgreSQL under the caller's identity, so Row Level Security (RLS) decides what the caller sees. The optimizer uses Google OR-Tools CP-SAT [5]. AI features use Anthropic Claude when a key is configured, with deterministic rules as the fallback. Render hosts the website and the API; Supabase hosts the database and sign-in.

Figure 2. System architecture: web app, API with background jobs, Supabase and the optional Claude integration.

    +---------------------+  HTTPS + token  +-------------------------+  SQL as role   +----------------------+
    | Web browser         |---------------->| NirnAIn API (FastAPI)   |--------------->| Supabase             |
    | React 19 SPA        |<----------------| jobs: CP-SAT, intake    | 'authenticated'| Postgres 17, RLS     |
    +---------------------+  JSON           +-------------------------+                +----------------------+

The team worked in short iterations ("rounds"). Each round had a written specification. Features were built on branches and merged only when every check passed: linting, strict typing, unit tests, database tests and the production build. The product owner made numbered decisions (D1 to D6) between rounds.

2 Related Work

Why not just use a scheduling tool? Because no single tool covers notes, optimization and change control.

In short: NirnAIn combines four research areas that are usually separate (Table 2).

• Scheduling. The critical path method (CPM) [6] ignores resource limits. The resource-constrained project scheduling problem (RCPSP) adds them; Brucker et al. [7] classify its models, and Hartmann and Briskorn [8] survey variants such as multimode and multi-skill problems. NirnAIn's problem is such a variant. Herroelen and Leus [9] stress stable re-planning after disruptions.
• Constraint programming. Interval variables and cumulative constraints model scheduling directly [10]. CP-SAT adds a SAT engine with lazy clause generation, a linear relaxation and parallel workers [11].
• Language models. LLMs extract structure from text with few examples [12] and are widely used in software engineering [13]. Meetings are hard to summarize faithfully [14]. Hallucination [15] and prompt injection [16] are the main risks.
• Commercial tools. Microsoft Project [17] schedules tasks the PM types in. Jira [18] manages backlogs and issues.

|                     |                     |                    | infeasibility        |                      |
+---------------------+---------------------+--------------------+----------------------+----------------------+
| CPM [6] and RCPSP   | A network built by  | None (CPM);        | Rarely exposed to    | Outside the model    |
| models [7]          | an analyst          | optimized (RCPSP)  | users                |                      |

4 Models

How do we get from a meeting transcript to an optimal, explainable plan?

In short: five models work in sequence: an intake pipeline, a data model, a CP-SAT optimizer, AI models with fallbacks, and visual views.

4.1 ETL and Intake Pipeline

In short: extract text, transform it into evidence-backed scope items, and load them for review (Figure 3).

Figure 3. The intake pipeline as extract, transform and load stages.

    +------------------------+       +--------------------------+       +---------------------------+
    | Extract: upload, text  |------>| Transform: Claude or     |------>| Load: scope_items, PM     |
    | up to 200,000 chars    |       | rules, evidence check    |       | review, then the WBS      |
    +------------------------+       +--------------------------+       +---------------------------+

• Extract. Files are streamed. PDF and Word text is extracted; captions lose timings and keep speakers.
• Transform. An intake job (one per project at a time) calls Claude or the rule-based extractor. Each item must quote the notes verbatim, or it is labeled inferred.
• Load. Items land in six categories. The PM accepts, edits or removes each one; pending items block the WBS step.

4.2 Data Model

In short: a normalized relational schema for operations, with a dimensional view for analytics (Figure 4, Table 7).

Figure 4. Core entities (12 of 25 tables) and their one-to-many relationships.

    +---------------+ 1:N +----------+ 1:N +-----------+ 1:N +-------------------+
    | organizations |---->| projects |---->| wbs_nodes |---->| dependencies      |
    +---------------+     +----------+     +-----------+     +-------------------+

The WBS is a tree with codes computed by a view. Links that cross projects are blocked by database triggers. Each optimization run stores a snapshot of its inputs, so every plan can be reproduced. Following Kimball and Ross [21], the planning data also forms a star schema.

4.3 Optimization Model

In short: CP-SAT decides who works on each package and when, at the lowest cost that respects the PM's limits (Table 8, Figure 5).

Table 8. The CP-SAT formulation at a glance (time in working days, money in cents).

+---------------------+----------------------------------------------------------------------------------------+
| Part                | Formulation                                                                            |
+---------------------+----------------------------------------------------------------------------------------+
| Decisions           | x[t,r] = 1 if work package t goes to candidate r; start s[t] and end e[t]; makespan C  |
| Assignment          | Exactly one candidate per package; one optional interval per working mode              |
| Durations           | Depend on the person: part-timers take effort / daily hours, rounded up; each skill    |
|                     | level above the minimum is 10% faster (max 30%), each level below 25% slower (decision |
|                     | D5)                                                                                    |
| Capacity            | Daily load per person, plus bookings on other projects, within their hours; Can flex   |
|                     | allows up to 125% as paid overtime                                                     |
| Dependencies        | FS, SS, FF and SF links with lags on real starts and ends                              |
| Deadline and budget | Hard: C <= deadline; labor cost <= budget minus reserve. Soft: a penalty per day late  |
|                     | or per $1,000 over                                                                     |
| Objective           | Minimize labor cost + $200 per day of makespan + soft penalties + $500 per package     |
|                     | moved off its owner + $10 per day of start shift                                       |
| Window              | Unfinished work starts no earlier than today; finished work keeps its dates (decision  |
|                     | D4)                                                                                    |
+---------------------+----------------------------------------------------------------------------------------+

Figure 5. From reviewed inputs to an applied plan, with the blocker and remedy loop.

    +-------------+   +--------------+   +--------------+   +------------------------+
    | Inputs and  |-->| Frozen run,  |-->| CP-SAT solve |-->| Apply as Plan vN       |
    | SHA-256 hash|   | inputsHash   |   |              |   | (409 if inputs changed)|
    +-------------+   +--------------+   +--------------+   +------------------------+

Three features make the model useful to a PM:

• Every blocker named. If no plan fits, each hard limit sits behind an assumption literal. CP-SAT returns conflicting sets, up to five, in plain English.
• Priced remedies (decision D2). A slipping or infeasible plan gets options: a contractor (confirmed rate or a $175 per hour estimate), overtime up to 25% at 1.5 times the rate, or accepting the date. The PM decides.
• No stale plans. The inputs hash (SHA-256, Listing 2) fingerprints exactly what the solver used. Applying a run whose inputs changed is refused with HTTP 409 (Listing 3).

Changes follow five steps: record, analyze, re-plan from today, compare with the plan in force, and approve or reject. Re-plans stay close to the plan in force because moving tasks and owners costs money in the objective.

4.4 AI Models

In short: Claude powers five features, each with a rule-based fallback that uses no tokens (Figure 6, Table 9).

Figure 6. One AI call: user text in a data block, Claude or the rules, then evidence grounding.

    +-------------+   +-------------+   +------------------+   +--------------------+
    | Notes, docs |-->| Data block  |-->| Claude or rules  |-->| Evidence grounding |
    +-------------+   +-------------+   +------------------+   +--------------------+

Table 9. AI features with Claude and without it.

+---------------------------+------------------------------------+-----------------------------------------+
| Feature                   | With Claude                        | Rule-based fallback                     |
+---------------------------+------------------------------------+-----------------------------------------+
| Project draft from notes  | Fields with their quotes           | Patterns; never invents a value         |
| Intake (scope items)      | Category, quote and evidence label | Headings and keywords; at most 60 items |
| WBS generation and review | Proposes and reviews packages      | Template and structural checks          |
| Change detection          | Reads new meeting notes            | Only values a sentence states           |
| Planning assistant        | Answers from project data          | Reports "unavailable"                   |
+---------------------------+------------------------------------+-----------------------------------------+

Claude returns structured output validated against a schema [22]. User text sits in a delimited data block with angle brackets escaped, which guards against prompt injection [16]. Quotes are re-checked against the notes, which guards against hallucination [15].

5.1 Case Study: Plan v1 to Plan v2

In short: losing a quarter of one developer's time cost $10,800 and finished ten days earlier (Table 10).

The Enterprise Data Platform project has a $375,000 budget and a hard deadline of September 30, 2027. Intake produced 20 accepted scope items, each with its quote. The WBS has 5 deliverables, 15 work packages and 45 weeks of effort. A contracted SAP specialist covers a skill nobody on the team has.

Then the Steering Committee cut Tom Rivera's time from 32 to 24 hours per week. The re-plan slipped, so the app offered priced options. The PM approved bringing in a contractor, which became Plan v2 (Figure 8).

Listing 1. CP-SAT model build: tasks, capacity, dependencies, makespan, deadlines, budget and the objective. Source: backend/app/optimization/builder.py, lines 94–110.

        def build(self) -> Variables:
            """Add every variable and constraint; the main model also gets its objective."""
            problem, model = self.problem, self.model
            variables = Variables(start={}, end={}, assign={})
            for task in problem.tasks.values():
                self._task(task, variables)
            self.workload.close()
            self._dependencies(variables)
            makespan = model.new_int_var(0, problem.horizon, "makespan")
            for task_end in variables.end.values():
                model.add(makespan >= task_end)
            self.penalize(makespan * MAKESPAN_CENTS_PER_DAY)
            self._deadlines(variables, makespan)
            self._budget(variables.assign)
            if not self.explain:
                model.minimize(cp_model.LinearExpr.sum(self._terms))
            return variables

Listing 2. The inputs hash: the SHA-256 fingerprint of exactly what the solver uses. Source: backend/app/optimization/inputs.py, lines 163–184.

    def inputs_hash(planning_input: PlanningInput) -> str:
        """SHA-256 of what the solver will use (other projects' bookings and today excluded).

        Hours, type, rates and skills of every person are part of it, so editing
        any of them invalidates a confirmed sheet.
        """
        snapshot = planning_input.to_snapshot()
        snapshot.pop("allocations", None)
        # The day it is computed isn't an input: the hash must not change overnight.
        snapshot.pop("today", None)
        # Applying a plan writes its assignees as the packages' owners and keeps finished work at
        # the plan's dates. Those are the plan's own output (owners are only a "don't reassign"
        # preference to the solver), so applying a plan must not make that same plan look stale.
        for task in snapshot["tasks"]:
            for plan_written_field in ("owner_id", "applied_start", "applied_end"):
                task.pop(plan_written_field, None)
        # No reserve changes nothing the solver does: such inputs keep the hash they had
        # before the reserve reached the solver.
        if not planning_input.constraints.contingency_pct:
            snapshot["constraints"].pop("contingency_pct", None)
        canonical = json.dumps(snapshot, sort_keys=True, separators=(",", ":"), default=str)
        return hashlib.sha256(canonical.encode()).hexdigest()

Listing 3. API endpoint that applies a run and refuses outdated inputs with HTTP 409. Source: backend/app/api/v1/plan.py, lines 56–78.

    async def apply_run(
        project_id: ProjectId, run_id: RunId, runs: OptimizationRuns, plans: Plans
    ) -> OptimizationRun:
        """Make a successful run the next plan version (409 when its inputs are outdated)."""
        candidate = await runs.get(project_id, run_id)
        if candidate is None:
            raise NotFoundError(RUN_NOT_FOUND)
        if not await runs.can_write(project_id):
            raise ForbiddenError("You do not have permission to apply this run")
        # Unsolved or already applied runs are refused by the apply function itself (422).
        if candidate.status in SUCCESSFUL and candidate.version is None:
            project = await runs.project(project_id)
            if project is None:
                raise NotFoundError("Project not found")
            saved = await runs.load_input(project, datetime.now(UTC).date())
            # A run without a recorded hash can't prove it is current: it is outdated too.
            if candidate.options.get("inputsHash") != inputs_hash(saved):
                raise ConflictError(STALE_RUN_DETAIL)
        await plans.apply(run_id)
        run = await runs.get(project_id, run_id)
        if run is None:
            raise NotFoundError(RUN_NOT_FOUND)
        return run

Listing 4. Row Level Security policies on the projects table. Source: supabase/migrations/20260924000200_projects.sql, lines 141–165.

    alter table public.projects enable row level security;

    create policy "projects: readable per visibility rules"
      on public.projects for select to authenticated
      using ((select private.can_read_project(id)));

    create policy "projects: non-viewers can create in their org"
      on public.projects for insert to authenticated
      with check (
        (select private.has_org_role(org_id, array['owner', 'admin', 'pm', 'member']::public.org_role[]))
        and created_by = (select auth.uid())
      );

    create policy "projects: writers can update"
      on public.projects for update to authenticated
      using ((select private.can_write_project(id)))
      with check ((select private.is_org_member(org_id)));

    create policy "projects: admins or creator can delete"
      on public.projects for delete to authenticated
      using (
        (select private.has_org_role(org_id, array['owner', 'admin']::public.org_role[]))
        or created_by = (select auth.uid())
      );
