1. Sign in to GitHub from the terminal (once)

GitHub doesn't accept your account password for git push. Use either a personal access token over HTTPS (1A, simplest) or an SSH key (1B).

1A. HTTPS with a personal access token (recommended)

1. On GitHub, click your picture → Settings → Developer settings → Personal access tokens → Fine-grained tokens → Generate new token.
2. Fill in:
  ◦ Token name: nirnain-upload
  ◦ Expiration: 30 days
  ◦ Resource owner: Dogiparthi-Sharada
  ◦ Repository access: Only select repositories → AI-Assisted-Project-Planning-Platform (for option B, create the new repository first (step B1) and select it too)
  ◦ Permissions → Repository permissions:
    ▪ Contents: Read and write (needed to push branches)
    ▪ Workflows: Read and write (needed when a push creates or changes .github/workflows/ci.yml: always for option B, and for the CI fix in step A7)
    ▪ Metadata: Read-only (added automatically)
3. Click Generate token and copy it right away. GitHub shows it only once. Keep it in your password manager, never in a file in the repository.
  Classic token instead? Tokens (classic) → Generate new token (classic) with the scopes repo (or public_repo if the repositories are public) and workflow.
4. Make git remember the token for one hour, in memory only (not on disk; the build machine is shared):
      git config --global credential.helper 'cache --timeout=3600'
5. Test it. When git asks, enter your GitHub user name, and paste the token as the password:
      cd /home/dog107433/AI-Assisted-Project-Planning-Platform
      git ls-remote sharada HEAD

✅ Check it worked: one line with a 40-character commit hash followed by HEAD. "Authentication failed" means the user name or token is wrong, or the token doesn't include this repository.

1B. SSH key (alternative)

Create a key: press Enter to accept the file name, and choose a passphrase. Then show the public key and copy the whole line it prints:

    ssh-keygen -t ed25519 -C "<your-email>"
    cat ~/.ssh/id_ed25519.pub

On GitHub: Settings → SSH and GPG keys → New SSH key, paste the line, then Add SSH key. Then:

    ssh -T git@github.com
    cd /home/dog107433/AI-Assisted-Project-Planning-Platform
    git remote set-url sharada git@github.com:Dogiparthi-Sharada/AI-Assisted-Project-Planning-Platform.git
    git ls-remote sharada HEAD

✅ Check it worked: ssh -T answers Hi Dogiparthi-Sharada! You've successfully authenticated…, and git ls-remote prints a commit hash and HEAD.

2. Safety checks before any push

What must NOT be uploaded

• .vscode/ – Why: Your editor's local settings. How it stays out: Untracked: never git add it.
• The .code-workspace file – Why: Local VS Code workspace with paths on this machine. How it stays out: Untracked: never git add it.
• The mockup zip (for example NirnAIn_demo_handoff_2026-11-13.zip) and any other .zip, such as the QA pack – Why: Large hand-off files, not source code. How it stays out: Untracked: never git add them; share them separately if needed.
• Any .env file (.env.local, backend/.env, supabase/.env, …) – Why: Real keys and passwords. How it stays out: .gitignore ignores .env*; only the .env.example templates are tracked.
• The lead's session folder (~/.copilot/session-state/…) – Why: It holds secrets (localstack/secrets.env, localstack/env/*.env, the Claude key) and the local database files. How it stays out: It is outside the repository: never copy anything from it into the repository.
• The helper branches (nirnain/*, preview/live, demo/backend-*, demo/working-demo) – Why: Work-in-progress copies, already merged. How it stays out: Push only demo/mockup; never git push --all.

Untracked files are never uploaded by git push; only commits are. The risk is adding them by accident with git add ., git add -A or git commit -a, so don't use those commands in this repository.

A6. Before merging: fix CI's database deploy (--remote)

Merging into main starts CI on main. Because this pull request changes supabase/, the Deploy job then runs supabase db push against production. Two things must be ready first:

1. The command needs --remote with the newer Supabase CLI. The job installs the CLI version latest. In the current CLI, supabase db push and supabase migration list target the local database unless you pass --remote. Before changing a hosted database, db push also asks for confirmation; --yes confirms without a prompt. The hosting guide already uses db push --remote for the same reason (DEPLOY_DEMO.txt, step 1.5). The repository owner (or you, with the Workflows token permission) changes the last steps of .github/workflows/ci.yml to:
            - name: Show pending migrations
              run: supabase migration list --remote --password "$SUPABASE_DB_PASSWORD"
            - name: Apply migrations
              run: supabase db push --remote --yes --password "$SUPABASE_DB_PASSWORD" --include-all
  Do this as a commit on demo/mockup (it then appears in this pull request) or as a separate small pull request first. Changes under /.github/ also need the code owner's approval.
2. The production secrets must point at the new Supabase project. On the team repository: Settings → Environments → production: the secrets SUPABASE_ACCESS_TOKEN and SUPABASE_DB_PASSWORD and the variable SUPABASE_PROJECT_REF. The old Supabase project no longer exists. Only repository admins can change these.

If the new project's tables were created with the SQL Editor instead of the CLI, don't let CI push migrations to it. The hosting guide explains why (step 1.5, Option B).

✅ Check it worked: after the merge, the Actions tab on the team repository shows the run on main with "Deploy · push migrations to production" green, and its "Apply migrations" log ends without errors.
