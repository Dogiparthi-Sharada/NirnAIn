1 Introduction and Business Problem

1.1 Background and Motivation

Most projects begin in meetings. A sponsor describes an objective, stakeholders add requirements, and someone mentions a deadline, a budget ceiling or a person who can only work part-time. The project manager (PM) must then turn these notes, transcripts and documents into a charter, a scope statement, a work breakdown structure (WBS), a staffing plan and a schedule. The Project Management Institute treats planning, scope definition and the management of change as core performance domains of project work [1], yet in practice the translation from conversation to plan is still largely manual. It is slow, and the link between a planning decision and the sentence that motivated it is usually lost.

Plans also go stale quickly. People are shared between projects, so a schedule that looked feasible on paper can overbook an engineer who is committed elsewhere. Mid-project changes such as a reduced allocation, a new requirement or a moved deadline are often absorbed informally: the schedule is edited by hand, the cost impact is estimated later, and nobody can say precisely which version of the plan was approved and why. The consequences can be severe. Flyvbjerg and Budzier [2] describe an enterprise system migration whose proposed budget was less than $5 million but which ended in a $192.5 million charge against earnings, and they argue that information technology projects carry far more risk than their sponsors assume.

NirnAIn is an AI-assisted project planning platform that addresses this gap. It reads meeting notes and documents, extracts a project charter and scope with verbatim evidence, helps the PM build a WBS, and then uses mathematical optimization to produce a schedule and staffing plan that respects the project's limits. When something changes mid-project, NirnAIn re-plans with minimal disruption, prices the options for keeping the date, and keeps every approved plan as a numbered version.

1.2 Business Problem

The business problem addressed in this report has four parts:

• Manual planning from unstructured input. Requirements, constraints and risks are buried in free text. Extracting them is time-consuming, and errors or omissions propagate into the WBS and the schedule.
• Resource conflicts. Schedules are often built as if each person were available full-time for one project. Part-time allocations, skill levels and commitments to other projects are considered informally, if at all.
• Infeasible or opaque plans. When the budget, the deadline and the available people cannot all be satisfied, conventional tools rarely explain why, and they do not quantify the cost of the alternatives.
• Uncontrolled change. Mid-project changes are applied without a consistent record of what changed, what the new plan costs, and which plan is in force.

1.3 Objectives, Scope and Research Questions

The project had five objectives. O1: turn meeting notes and documents into reviewable scope items, each tied to its source quote. O2: support the construction of a three-level WBS with durations, owners and skill requirements. O3: compute an optimized schedule and staffing plan that honors hard constraints, explains infeasibility and prices remedies. O4: provide controlled, versioned change management (record, analyze, re-plan, compare and approve). O5: deliver the system as a secure, multi-tenant web application that is tested and deployed with production engineering practices. 1.4 Solution Overview

NirnAIn is a three-tier web application (Figure 2). The browser runs a React [3] single-page application that signs in with Supabase Auth and calls the NirnAIn API with the user's access token. The API, written in Python with FastAPI [4], validates every request, runs each query in PostgreSQL under the caller's identity so that Row Level Security (RLS) decides what the caller can read and write, and runs long work (optimization, intake and AI jobs) as background jobs. The optimizer is built on Google OR-Tools CP-SAT [5]. The AI features use Anthropic Claude when an API key is configured; every AI feature also has a deterministic, rule-based fallback, so the full workflow runs without a key. The website and the API are hosted on Render (a static site and a web service), and the database and authentication on Supabase.

The team followed a disciplined engineering process. Work was specified in short written specifications per iteration ("rounds"), developed on feature branches and merged into an integration branch only after every automated check had passed: linting and formatting (ruff), strict static typing (mypy), the backend test suite (pytest), database tests (pgTAP) inside rolled-back transactions, TypeScript type checking and the production build. The product owner made explicit, numbered decisions between rounds (D1 to D6, described in Section 4.3), and quality assurance (QA) ran in rounds as well, including an independent QA pack written from the business side. The integration branch was then merged into the protected main branch, from which both services deploy automatically.

2 Related Work

2.1 Network-Based Project Scheduling

Modern project scheduling began with network models. The critical path method (CPM) of Kelley and Walker [6] represents a project as activities linked by precedence relations and computes the longest path, which determines the earliest completion date and the activities without slack. The Program Evaluation and Review Technique (PERT) [7] added probabilistic activity durations. Both methods are typically communicated with Gantt charts, whose history and lasting influence are reviewed by Wilson [8]. CPM and PERT assume that resources are unlimited: they schedule activities as early as precedence allows, regardless of whether the people needed are available. NirnAIn keeps the vocabulary of these methods (finish-to-start, start-to-start, finish-to-finish and start-to-finish dependencies with lags, a critical path and a Gantt view) but removes the unlimited-resource assumption.

2.2 The Resource-Constrained Project Scheduling Problem

When activities compete for limited resources, scheduling becomes the resource-constrained project scheduling problem (RCPSP). Blazewicz, Lenstra and Rinnooy Kan [9] showed that such problems are strongly NP-hard, which rules out simple exact algorithms for large instances. Brucker et al. [10] introduced a widely used notation and classification of RCPSP models and methods, and Hartmann and Briskorn [11] surveyed its many variants, including multimode problems in which an activity's duration depends on the mode (for example, the resource) chosen, multi-skill problems and problems with time-varying capacity. Kolisch and Hartmann [12] compared heuristics on standard benchmark instances. NirnAIn's planning problem is a multimode, multi-skill RCPSP variant: a work package can be performed by any qualified person, its duration depends on that person's availability and proficiency, and each person's daily capacity is shared with other projects.

Real projects are also subject to change. Herroelen and Leus [13] surveyed scheduling under uncertainty and distinguished proactive approaches, which build robust baseline schedules, from reactive approaches, which repair a schedule after a disruption. A repaired schedule should stay close to the baseline; NirnAIn's re-planning follows this stability-aware approach by penalizing changes of owner and shifted start dates.

2.3 Constraint Programming and CP-SAT

Constraint programming (CP) has become a leading technology for scheduling. Laborie et al. [14] describe IBM ILOG CP Optimizer, whose interval variables, optional intervals and cumulative constraints model activities, alternative resources and capacity directly. Google's CP-SAT solver, part of the open-source OR-Tools suite [5], combines constraint propagation with a Boolean satisfiability (SAT) engine based on lazy clause generation, a linear programming relaxation and a portfolio of parallel search workers [15]. CP-SAT supports optional intervals, cumulative constraints and assumption literals; the last allow a solver to return a subset of constraints that cannot hold together, which NirnAIn uses to explain infeasible plans. Because OR-Tools is free and open source, it runs in continuous integration and on free hosting without a license server.

2.4 Language Models for Requirements and Meeting Understanding

Large language models have made it practical to extract structure from unstructured text with little task-specific training. Brown et al. [16] showed that sufficiently large models perform many language tasks from a few examples given in the prompt. Hou et al. [17] reviewed the use of LLMs across software engineering, including requirements engineering tasks such as requirements classification and specification. Zhong et al. [18] introduced QMSum, a benchmark for query-based meeting summarization, which shows that meeting transcripts are long, multi-speaker and difficult to summarize faithfully.

Two risks limit the use of LLMs in planning. The first is hallucination: Ji et al. [19] survey the many ways in which generated text can be unfaithful to its source. The second is prompt injection: Greshake et al. [20] demonstrate that instructions hidden in data processed by an LLM-integrated application can take control of its behavior. NirnAIn addresses both risks by design: every extracted scope item must carry a quote that occurs verbatim in the notes, user text is placed in a delimited data block that the system prompt declares to be data, and the model's output is constrained to a schema with structured outputs [21].

2.5 Commercial Tools and the Gap NirnAIn Fills

Desktop and cloud scheduling tools such as Microsoft Project [22] support Gantt-based critical-path scheduling, resource assignment and leveling, while work-management tools such as Jira [23] manage backlogs, issues and team workflows. These tools start from tasks that a person has already typed in and repair resource conflicts with heuristics rather than optimizing cost and date against explicit hard and soft constraints (Table 2).

Three design choices matter for the rest of the report. First, links between the rows of a project (dependencies, WBS parents, owners, scope items, milestones, team members and skills) are checked by database triggers so that they cannot point into another project, and unknown and foreign identifiers receive the same error so that identifiers cannot be probed. Second, AI estimates are stored but count only after the PM confirms them, so the optimizer never uses an unreviewed number. Third, each optimization run stores a snapshot of its inputs, so every plan can be reproduced.

Units are fixed: money is stored as integer cents (bigint), durations as integer working days (a week is five working days), timestamps as timestamptz, and load inside the optimizer in tenths of an hour, so the solver works only with integers. JSON uses camelCase names and errors use the RFC 7807 problem+json format. Missing data is never invented: untracked values are shown as "Not tracked yet", and evidence labels tell the PM how much to trust each extracted item.

Data security is part of data quality: the API verifies the Supabase access token and executes each request as the database role authenticated with the caller's claims, so RLS policies decide which rows a user can see [24], [25]. Logs exclude tokens, uploaded text, notes, model answers and SQL parameters.

4 Models

This chapter presents the models that turn the data of Chapter 3 into plans: the intake pipeline (an extract-transform-load process), the relational and dimensional data models, the CP-SAT optimization model, the AI models with their rule-based fallbacks, and the visualizations that present the results.

4.1 ETL and Intake Pipeline

The intake pipeline converts unstructured documents into structured scope and, after review, into a WBS. It follows the classic extract, transform and load pattern (Figure 3).

Figure 3. The intake pipeline as extract, transform and load stages, from uploaded documents to scope items and the WBS.

    EXTRACT                          TRANSFORM                          LOAD AND REVIEW
    +------------------------+       +--------------------------+       +---------------------------+
    | Upload or paste        |       | Intake run (job)         |       | scope_items               |
    | PDF, DOCX, VTT, SRT,   |------>| Claude structured output |------>| quote + evidence label;   |
    | TXT up to 100 MB       |       | or rules extractor       |       | PM accepts, edits, removes|
    +------------------------+       +--------------------------+       +---------------------------+
                |                                 |                                   |
                v                                 v                                   v
    +------------------------+       +--------------------------+       +---------------------------+
    | Text extraction        |       | Evidence grounding       |       | WBS (wbs_nodes)           |
    | <= 200,000 characters  |       | verbatim quote or        |       | generate, validate,       |
    | caption cleanup        |       | label 'inferred'         |       | confirm estimates         |
    +------------------------+       +--------------------------+       +---------------------------+

Extract. Files are streamed rather than read into memory in one piece, and the file type is determined from the extension, with the MIME type as a fallback. PDF text is extracted with pypdf and Word text with python-docx. WebVTT and SRT captions lose their headers, cue numbers and timings, voice tags become speaker labels, and consecutive cues by the same speaker are merged so that sentences are not cut at cue boundaries. At most 200,000 characters are kept per document; a longer document is flagged as truncated and the interface says so. Extraction failures return a fixed user-facing message and log only the document identifier, size, kind and the class of the error.

Transform. An intake run is a background job; the database allows only one active run per project. When an API key is configured, Claude receives the notes and documents inside a delimited data block and returns scope items in a fixed schema (Section 4.4). Without a key, or when the call fails, a deterministic rules extractor is used instead. It reads headings and the bullets beneath them (for example, a heading such as "Requirements" assigns its bullets to the requirement category), classifies remaining sentences by keywords, treats transcripts one speaker turn at a time, removes near-duplicates and keeps at most 60 items, shared fairly across categories. Both paths pass through evidence grounding: an item keeps its source quote only if that quote occurs in the notes, ignoring case, whitespace and typographic variants of quotes and dashes; otherwise, the quote is dropped, and the item is labeled inferred.

Load and review. Items are stored in scope_items in six categories (objectives, requirements, deliverables, constraints, risks and missing information). The PM accepts, edits or removes each one; pending items block the WBS step, so the plan is always built from reviewed scope. The WBS can then be generated (by Claude or by a deterministic template), edited as a three-level tree, and validated by built-in structural checks plus an optional Claude review. Durations are entered in weeks and stored as working days, and AI estimates count only after the PM confirms them.

4.3 Optimization Model

4.3.1 Problem Formulation

The optimizer receives a frozen planning input and decides who performs each unfinished work package and when. Time is measured in working days from the project start; money in cents; load in tenths of an hour. Table 8 defines the notation used below. The formulation mirrors the implementation in the optimization package of the API, which is pure Python with no database or web dependencies.

Table 8. Sets, parameters and decision variables of the CP-SAT model.

+----------------+---------------------------------------------------------------------------------------------+
| Symbol         | Meaning                                                                                     |
+----------------+---------------------------------------------------------------------------------------------+
| T              | Unfinished work packages; finished packages keep the dates of the plan in force             |
| R(t)           | Candidates for package t: team members and, when allowed, contractor profiles               |
| h(t), d(t)     | Effort hours and WBS duration (working days) of package t                                   |
| q(r), p(t,r)   | Daily capacity of person r in tenths of an hour; pace of r on t in percent of the WBS       |
|                | effort                                                                                      |
| d(t,r), c(t,r) | Duration of t when done by r, and its labor cost in cents                                   |
| Rel, H         | Release day (today, or the project start if later) and the planning horizon                 |
| x[t,r]         | Boolean: package t is assigned to candidate r                                               |
| s[t], e[t]     | Integer start day and exclusive end day of package t                                        |
| C              | Makespan: the last end day of the plan                                                      |
+----------------+---------------------------------------------------------------------------------------------+

The horizon H is chosen so that a serial schedule always fits: it is the release day plus the sum of every package's longest candidate duration, the absolute values of all lags, the last day booked on other projects and one working week. The core constraints are:

    (1)  sum over r in R(t) of x[t,r] = 1, for every package t

    (2)  Rel <= s[t] <= H - min over r of d(t,r)

    (3)  e[t] = s[t] + d(t,r) for the chosen candidate r (one optional interval per mode)

    (4)  C >= e[t] for every package t

Each candidate is represented by optional interval variables, one per mode: a regular mode at the person's daily hours, a flexible mode up to 25% above those hours (only under Can flex capacity), and stretched modes that fit around bookings on other projects. Exactly one interval of the chosen candidate is present.

Capacity. For each employee, a cumulative constraint over that person's intervals ensures that the daily load of overlapping work, plus fixed blocks for hours already booked on other projects, does not exceed the daily capacity q(r), which is the weekly hours given to the project divided by the working days per week. Contractor profiles have no capacity limit: they stand for as many hired specialists as needed.

Dependencies. For a link from p to q with lag L, the four standard types are enforced on the real starts and ends, so that a stretched predecessor pushes its successors:

    (5)  FS: s[q] >= e[p] + L;   SS: s[q] >= s[p] + L;   FF: e[q] >= e[p] + L;   SF: e[q] >= s[p] + L

Deadline, milestones and budget. With a hard deadline D, C <= D; each hard milestone bounds the end of the packages beneath it. The labor cost is a linear expression in the assignment variables, and under a hard budget it is bounded by the budget less the contingency reserve and by the labor cap:

    (6)  K = sum over t, r of c(t,r) * x[t,r];   K <= B - reserve(B);   K <= labor cap

4.3.2 Durations, Skill Levels and Cost

Durations depend on the person, which makes the problem a multimode RCPSP [11]. Two rules apply. The first is the part-time stretch: a person who cannot provide the package's daily demand takes the effort divided by their daily hours, rounded up to whole working days, so reducing someone's hours lengthens the plan instead of overbooking that person. The second is skill speed (product-owner decision D5): the WBS effort is defined for a person at the package's minimum proficiency; each level above the minimum is 10% faster, up to 30%, and each level below it (allowed only when skills are set to Can flex) is 25% slower. The weakest required skill sets the pace, and the pace scales the hours and therefore the cost (Figure 6). For example, a person at proficiency 5 on a package that requires level 2 needs 70% of the effort, so a 10-day package takes 7 days. Contractor profiles always work at the WBS pace.

Figure 6. Effort and duration as a percentage of the WBS estimate, by the difference between a person's proficiency and the package's minimum level (decision D5).

    margin  -2    -1    0     +1    +2    +3    +4
    effort  150%  125%  100%  90%   80%   70%   70%

The cost model counts labor only. The cost of package t done by r is c(t,r) = round(h(t) x p(t,r) / 100 x rate(r)). Employees are costed at the company rate on record or the standard $85 per hour; contractors at their own rate (decision D1). Overtime, possible only under Can flex capacity, is billed at 1.5 times the employee rate and at the normal rate for contractors. The contingency reserve is held back from the budget and rounded up to the cent: with a $1,100 budget and a 10% reserve, a plan may cost at most $990, so a $1,000 plan is infeasible by $10.

4.3.3 Objective Function

The model minimizes a single cost in cents (Table 9). Besides the labor cost, it rewards short plans, penalizes the soft limits the PM allowed to bend, and keeps re-plans close to the plan in force so that changes remain few and explainable.

    (7)  minimize K + 20,000 C + soft penalties + 50,000 x (owner changes) + 1,000 x sum over t of (s[t] - s0[t])

Table 9. Objective terms and their default weights (all in cents).

+-----------------------------------+------------------------------------+-------------------------------------+
| Term                              | Weight                             | Purpose                             |
+-----------------------------------+------------------------------------+-------------------------------------+
| Labor cost K                      | 1 per cent                         | Prefer the cheapest feasible        |
|                                   |                                    | staffing                            |
| Makespan C                        | 20,000 per working day ($200)      | Prefer earlier completion           |
| Package moved off its current     | 50,000 per package ($500)          | Stability of re-plans               |
| owner                             |                                    |                                     |
| Start shift relative to the       | 1,000 per working day ($10),       | Stability; later starts cost and    |
| baseline start s0[t]              | linear                             | earlier starts are credited         |
| Soft deadline or milestone        | 50,000 per working day late        | Allow a late finish only if it pays |
|                                   | (default $500)                     | off                                 |
| Soft budget                       | 100,000 per $1,000 over (default)  | Allow overspending only if it pays  |
|                                   |                                    | off                                 |
| Soft skills                       | 200,000 per missing proficiency    | Prefer qualified people             |
|                                   | level                              |                                     |
| Can flex capacity                 | 10,000 per overtime hour plus the  | Overtime only when it keeps a date  |
|                                   | overtime premium (default)         | or saves money                      |
| Target date (remedy runs only)    | Set per remedy                     | Try hard to keep the date being     |
|                                   |                                    | protected                           |

The solver is given the baseline start and owner of every package as hints. Runs use a 20-second time limit by default, four parallel workers (one on the free hosting tier) and a fixed random seed, and every run stores these settings so that it can be reproduced. A status of OPTIMAL means that CP-SAT proved optimality; FEASIBLE means that the time limit was reached with a plan in hand. After a feasible plan is found under Can flex capacity, a short polishing step removes overtime that neither keeps a date nor saves money.

4.3.5 Blockers and Priced Remedies

When no plan satisfies the hard constraints, the PM needs to know every reason, not just one. NirnAIn rebuilds the model without its objective and places each hard constraint group (the deadline, each milestone, the budget, the labor cap, each package's required skill, each person's capacity and each dependency) behind an assumption literal. CP-SAT then returns a set of assumptions that cannot hold together, which is shrunk by deletion to a small conflicting core. The core's headline group is relaxed as if the PM had changed it, and the search repeats, up to five times, until the model becomes feasible. All cores are reported together in plain language, for example that the deadline, a missing SAP skill and a missing SOC 2 skill each block the plan.

When a plan is infeasible or finishes after its target date, the optimizer job re-solves relaxed copies of the frozen input and prices each option against the current plan (Table 11, decision D2). An option is offered only if it produces a plan, uses what it adds and, for a slipping plan, finishes earlier. Nothing is chosen automatically: the PM decides.

4.3.6 Baseline, Inputs Hash and Plan Versions

Re-planning is anchored in time and in the plan in force. The planning window starts on the project start date or today, whichever is later, so unfinished work never starts in the past, and finished work keeps the dates of the plan in force (decision D4). Applying a plan writes its owners and dates back to the WBS, so the next run uses the applied plan as its baseline and the stability terms of the objective keep tasks and owners in place where possible (decision D3).

To prevent a plan computed from outdated inputs from going into force, the API computes an inputs hash: the SHA-256 digest of the canonical JSON form of exactly what the solver uses (Listing 3). Bookings on other projects, the current date and the fields that applying a plan writes (owners and applied dates) are excluded, so that applying a plan does not make the same plan look outdated. Each run records the hash of its inputs. A run can start only from the inputs the PM reviewed on the inputs sheet; applying a run whose inputs have since changed is refused with HTTP 409 and the screen offers "Run again" (Listing 4); and approving a change is refused when either the plan in force or the inputs changed after the re-plan. Applied runs become numbered plan versions (Plan v1, v2 and so on), and applying writes weekly allocations with the hours actually planned in each week. 4.3.7 Change Control

Mid-project changes follow a five-stage workflow (Figure 8). A change is recorded from new meeting notes, direct edits or a progress update. It is analyzed to determine what changed, with quotes from the notes and the questions the PM must answer. The project is then re-planned from today with minimal disruption, the proposed plan is compared with the plan in force package by package, and the PM approves it, making it the next plan version, or rejects it and keeps the current plan. The change request's status moves from draft through analyzing, ready, replanning and proposed to approved, rejected or failed. A failed or infeasible change can always be dismissed.

4.4 AI Models

NirnAIn uses Anthropic's Claude models for five product features (Table 12). All calls go through a single module that sends a system prompt and the user content and receives either plain text (for the assistant) or a structured output validated against a Pydantic schema [21]. The model identifiers are configuration settings: one model is configured for intake and another for the remaining features. Every feature has a deterministic fallback that is used when no API key is configured or when a call fails; the fallback is labeled in the interface and in the stored record (model "rules") and consumes no tokens. Optimization, applying a plan and approving a change never call the language model.

The intake prompt illustrates the design. The system prompt instructs the model to act as a project-intake analyst, to treat everything inside the notes tags as data rather than instructions, to extract only concrete items that the notes support and never to invent facts, names, dates or figures. Each item must carry its evidence: the exact words of the notes that support it, copied character for character; an evidence label (stated when the quote says the item, inferred when the item is a reasonable reading, flagged when the item says more than the quote); a note explaining an inference or the unsupported addition; and, for flagged items, a suggested rewording limited to what the quote supports. The application then re-checks every quote against the notes, which guards against hallucinated evidence [19], and it escapes angle brackets in user text so that the text cannot close the data block, which guards against prompt injection [20].

The rule-based change detector was deliberately made strict after QA found that a permissive version could propose values that the notes did not support, such as reading a rejected proposal as a new budget. It now ignores sentences that reject or decline something, ignores values that follow "instead of", reads hours only from statements of the form "Name ... N hours a week" and treats "must hold" next to a date as a hard deadline.

6 Conclusions and Impact

6.1 Answers to the Research Questions

RQ1 (evidence-grounded intake). The results support a qualified yes: every scope item quotes the notes verbatim, so the PM can check it in seconds, and the deterministic fallback keeps the workflow testable without a model. On the walkthrough notes, which are organized under conventional headings, the rule-based extractor recovered all 20 intended scope items word for word. The Claude path is designed to the same evidence contract, but it was verified only by spot checks; a systematic evaluation of extraction quality on real meetings remains future work.

RQ2 (optimization). CP-SAT produced optimal plans for the demonstration projects in a fraction of a second, honored every hard limit, and named every independent blocker of infeasible projects in plain language. The QA pack's independent checks recomputed plan costs to the cent, and its reserve micro-oracle (a $1,100 budget with a 10% reserve makes a $1,000 plan infeasible) is reproduced exactly.

RQ3 (change control). The re-planning workflow handled the product owner's mid-project scenarios (changed hours, added and removed people, new specialists, moved deadlines, budget changes, scope growth and progress), and the inputs hash prevented outdated plans from being applied.

RQ4 (delivery). The platform runs as a multi-tenant SaaS application in which RLS isolates workspaces and automated tests cover the backend, the database and the end-to-end workflow; the one cross-workspace defect found by QA was fixed in both the API and the database.

6.2 Business Impact

For a project manager, NirnAIn shortens the path from a meeting to a defensible plan. Scope comes with its evidence, so reviews focus on judgment rather than transcription. The optimizer tests feasibility before commitments are made and turns trade-offs into explicit, priced choices: in the walkthrough, losing a quarter of one developer's time was resolved by adding a contractor for an extra $10,800 (6.2%), while the plan finished ten days earlier than before and stayed $190,200 under budget. Every approved plan is a numbered version with its inputs, so sponsors can see what changed, why and at what cost. For an organization, the shared view of people across projects reduces hidden overbooking, and the explanation of blockers supports better conversations about scope, budget and dates. These benefits are demonstrated on synthetic projects; quantifying them on real projects is future work.

6.4 Lessons Learned

Several lessons emerged. First, end-to-end testing should start in the first iteration, and progress should be measured as "tested and passing" rather than "built". Second, the mid-project story (change control, versions, the today anchor and finished work) is the heart of the product and belonged in the first specification rather than emerging from QA. Third, product decisions should be batched and frozen at fixed points; a requirement reversed within an hour cost rework. Fourth, test data must be isolated: a fresh workspace per suite run and rolled-back database tests removed false regressions. Fifth, "apply, then check the status" should be a standing regression test, because two defects arose when applying a plan changed its own inputs hash. Finally, an independent QA pack written from the business side found the defects that mattered most.

6.5 Future Work

The most valuable extensions follow from the limitations: working calendars with leave and holidays; actual hours, earned value and estimate at completion; fixed and infrastructure costs in the optimization model; audio transcription for meeting recordings; and team features (invitations, roles and an audit view). A systematic evaluation of the Claude extraction against annotated meeting transcripts, in the spirit of meeting-understanding benchmarks [18], would quantify RQ1. Robust scheduling [13] could replace single-point estimates, and a portfolio model could plan several projects jointly. A pilot with real project managers would measure the time saved.

Listing 1. CP-SAT model core: start, candidate assignment, duration modes and baseline terms of one work package. Source: backend/app/optimization/builder.py, lines 113–152.

        def _task(self, task: Task, variables: Variables) -> None:
            """Start, candidates and end of one task; its end follows whoever is chosen."""
            problem, model = self.problem, self.model
            # Unfinished work never starts before today, and ends by the horizon even with
            # the fastest candidate (a skilled person may beat the WBS duration, D5).
            shortest = min(
                (
                    problem.modes[task.id, resource.id].duration_days
                    for resource in problem.candidates[task.id]
                ),
                default=task.duration_days,
            )
            start = model.new_int_var(problem.release, problem.horizon - shortest, f"start[{task.id}]")
            options: dict[str, cp_model.IntVar] = {}
            ends: list[tuple[cp_model.IntVar, int]] = []
            for resource in problem.candidates[task.id]:
                gap = resource.skill_gap(task)
                if gap and self.constraints.skill_mode == "hard" and not self.explain:
                    continue  # unqualified: not a candidate
                chosen = model.new_bool_var(f"assign[{task.id},{resource.id}]")
                options[resource.id] = chosen
                ends += self.workload.candidate(task, resource, start, chosen)
                if gap and self.constraints.skill_mode == "hard":
                    # Explanation model: the unqualified candidate stays but is forbidden behind
                    # the skill's literal, so a missing skill can be named as a blocker.
                    for requirement in task.skills:
                        if resource.proficiency(requirement.skill_id) < requirement.min_proficiency:
                            self.guard(
                                model.add(chosen == 0),
                                ("skill", task.id, requirement.skill_id),
                                partial(conflicts.skill, problem, task, requirement),
                            )
                elif gap:
                    self.penalize(chosen * (gap * SKILL_GAP_CENTS_PER_LEVEL))
            # Exactly one candidate does the task; its literal switches on that person's intervals.
            model.add_exactly_one(options.values())
            self._baseline_terms(task, start, options)
            variables.start[task.id] = start
            variables.assign[task.id] = options
            variables.end[task.id] = self._task_end(task, start, ends)

Listing 2. Skill-level speed adjustment (decision D5). Source: backend/app/optimization/speed.py, lines 20–39.

    WBS_PACE = 100  # percent of the WBS effort
    FASTER_PER_LEVEL = 10
    MAX_FASTER = 30
    SLOWER_PER_LEVEL = 25


    def _margin(resource: Resource, requirement: SkillRequirement) -> int:
        """Return how many levels the person is above (positive) or below the skill's minimum."""
        return resource.proficiency(requirement.skill_id) - requirement.min_proficiency


    def pace_percent(resource: Resource, task: Task) -> int:
        """Percent of the WBS effort this person needs for the task (70 at best, 100 = WBS pace)."""
        if resource.kind != "employee" or not task.skills:
            return WBS_PACE
        gap = resource.skill_gap(task)
        if gap:
            return WBS_PACE + SLOWER_PER_LEVEL * gap
        surplus = min(_margin(resource, requirement) for requirement in task.skills)
        return WBS_PACE - min(FASTER_PER_LEVEL * surplus, MAX_FASTER)

Listing 3. The inputs hash: the SHA-256 fingerprint of exactly what the solver uses. Source: backend/app/optimization/inputs.py, lines 163–184.

    def inputs_hash(planning_input: PlanningInput) -> str:
        """SHA-256 of what the solver will use (other projects' bookings and today excluded).

        Hours, type, rates and skills of every person are part of it, so editing
        any of them invalidates a confirmed sheet.
        """
        snapshot = planning_input.to_snapshot()
        snapshot.pop("allocations", None)
        # The day it is computed isn't an input: the hash must not change overnight.
        snapshot.pop("today", None)
        # Applying a plan writes its assignees as the packages' owners and keeps finished work at
        # the plan's dates. Those are the plan's own output (owners are only a "don't reassign"
        # preference to the solver), so applying a plan must not make that same plan look stale.
        for task in snapshot["tasks"]:
            for plan_written_field in ("owner_id", "applied_start", "applied_end"):
                task.pop(plan_written_field, None)
        # No reserve changes nothing the solver does: such inputs keep the hash they had
        # before the reserve reached the solver.
        if not planning_input.constraints.contingency_pct:
            snapshot["constraints"].pop("contingency_pct", None)
        canonical = json.dumps(snapshot, sort_keys=True, separators=(",", ":"), default=str)
        return hashlib.sha256(canonical.encode()).hexdigest()

Listing 4. API endpoint that applies a run as the next plan version and refuses outdated runs. Source: backend/app/api/v1/plan.py, lines 46–78.

    @router.post(
        "/projects/{projectId}/optimization/runs/{runId}/apply",
        response_model=OptimizationRun,
        summary="Apply a successful run: it becomes the project's next plan version",
        responses={
            403: {"description": "Not a writer"},
            409: {"description": "The inputs changed since the run was solved"},
            422: {"description": "Not appliable"},
        },
    )
    async def apply_run(
        project_id: ProjectId, run_id: RunId, runs: OptimizationRuns, plans: Plans
    ) -> OptimizationRun:
        """Make a successful run the next plan version (409 when its inputs are outdated)."""
        candidate = await runs.get(project_id, run_id)
        if candidate is None:
            raise NotFoundError(RUN_NOT_FOUND)
        if not await runs.can_write(project_id):
            raise ForbiddenError("You do not have permission to apply this run")
        # Unsolved or already applied runs are refused by the apply function itself (422).
        if candidate.status in SUCCESSFUL and candidate.version is None:
            project = await runs.project(project_id)
            if project is None:
                raise NotFoundError("Project not found")
            saved = await runs.load_input(project, datetime.now(UTC).date())
            # A run without a recorded hash can't prove it is current: it is outdated too.
            if candidate.options.get("inputsHash") != inputs_hash(saved):
                raise ConflictError(STALE_RUN_DETAIL)
        await plans.apply(run_id)
        run = await runs.get(project_id, run_id)
        if run is None:
            raise NotFoundError(RUN_NOT_FOUND)
        return run

Listing 5. Row Level Security: the project-read function and the policies on the projects table. Source: supabase/migrations/20260924000200_projects.sql, lines 88–108, 141–165.

    create or replace function private.can_read_project(p_project_id uuid)
    returns boolean
    language sql
    stable
    security definer
    set search_path = ''
    as $$
      select exists (
        select 1
        from public.projects p
        join public.organization_members m
          on m.org_id = p.org_id and m.user_id = (select auth.uid())
        where p.id = p_project_id
          and (
            p.visibility <> 'confidential'
            or m.role in ('owner', 'admin')
            or p.pm_user_id = m.user_id
            or p.created_by = m.user_id
          )
      );
    $$;

    alter table public.projects enable row level security;

    create policy "projects: readable per visibility rules"
      on public.projects for select to authenticated
      using ((select private.can_read_project(id)));

    create policy "projects: non-viewers can create in their org"
      on public.projects for insert to authenticated
      with check (
        (select private.has_org_role(org_id, array['owner', 'admin', 'pm', 'member']::public.org_role[]))
        and created_by = (select auth.uid())
      );

    create policy "projects: writers can update"
      on public.projects for update to authenticated
      using ((select private.can_write_project(id)))
      with check ((select private.is_org_member(org_id)));

    create policy "projects: admins or creator can delete"
      on public.projects for delete to authenticated
      using (
        (select private.has_org_role(org_id, array['owner', 'admin']::public.org_role[]))
        or created_by = (select auth.uid())
      );


Listing 6. React query hooks that poll the latest optimization run and apply a run as the plan in force. Source: src/lib/queries/optimization.ts, lines 11–43.

    import { useMutation, useQuery, useQueryClient } from '@tanstack/react-query'
    import { apiFetch, apiFetchOrNull } from '../api'
    import type { OptimizationRun } from '../types'
    import { queryKeys } from './keys'
    import { runPath } from './paths'
    import { pollWhileRunning } from './polling'

    /** Latest optimization run for a project (`null` when none yet); polls while it is queued or running. */
    export function useLatestRun(projectId: string) {
      return useQuery({
        queryKey: queryKeys.latestRun(projectId),
        queryFn: ({ signal }) => apiFetchOrNull<OptimizationRun>(runPath(projectId, '/latest'), { signal }),
        refetchInterval: (query) => pollWhileRunning(query.state.data?.status),
      })
    }

    /**
     * Applies a run as the project's plan in force. The project, its WBS dates and every org list or
     * dashboard showing it change, so all of those are refreshed.
     */
    export function useApplyRun(projectId: string) {
      const queryClient = useQueryClient()
      return useMutation({
        mutationFn: (runId: string) =>
          apiFetch<OptimizationRun>(runPath(projectId, `/${encodeURIComponent(runId)}/apply`), { method: 'POST', json: {} }),
        onSuccess: (run) => {
          queryClient.setQueryData(queryKeys.latestRun(projectId), run)
          void queryClient.invalidateQueries({ queryKey: queryKeys.project(projectId) })
          void queryClient.invalidateQueries({ queryKey: queryKeys.wbs(projectId) })
          void queryClient.invalidateQueries({ queryKey: ['orgs'] })
        },
      })
    }
