NirnAIn - code index

How to use this file: Part 1 answers "where is the code for ...?" by feature, with the exact file and function. Part 2 lists every source file with its purpose and its functions, taken from the code's own headers and docstrings. Regenerate it with: python3.12 scripts/build_code_index.py

Layers: the browser app (src/) calls the API (backend/app/api/v1), which uses repositories (backend/app/repositories, database access under the caller's row-level security) and domain models (backend/app/domain); planning runs in the optimizer (backend/app/optimization) as a background job (backend/app/jobs); the schema lives in supabase/migrations.

PART 1 - WHERE IS THE CODE FOR ...?

A. Sign-in, security and data access (every step)
  * How does the API know who is calling? - backend/app/core/security.py -> TokenVerifier.verify(). Checks the Supabase access token's signature against the project's public keys (JWKS, ES256/RS256), its issuer, audience and expiry, and returns the caller.
  * How does each request obey row-level security? - backend/app/core/db.py -> apply_rls_context(). Runs the request's transaction as the `authenticated` role with the caller's JWT claims, so Postgres RLS policies decide what the user can read and write.
  * Who may read a project? - supabase/migrations/20260924000200_projects.sql -> private.can_read_project(). SQL helper used by the RLS policies: organization membership plus the project's visibility rules.
  * How are API errors returned? - backend/app/core/errors.py -> problem_response(). Every error is RFC 7807 problem+json with the request id; `map_db_error` turns Postgres SQLSTATEs into the right HTTP status.
  * How does the browser keep the session and protect pages? - src/auth/guards.tsx -> RequireAuth(). Sends a signed-out visitor to /login and back afterwards; the session itself lives in src/auth/AuthProvider.tsx.
  * How does the web app call the API? - src/lib/api.ts -> apiFetch(). Adds the user's bearer token and turns problem+json errors into a typed ApiError for the screens.

B. Step 1 - Create a project (form, notes, transcript or document)
  * Where are project details read from notes or a file? - backend/app/api/v1/drafts.py -> extract_project_draft(). Uses Claude when a key is configured, otherwise the labelled rules reader; the user reviews the draft.
  * How does the no-AI rules reader find name, budget and dates? - backend/app/drafts/rules.py -> rules_draft(). Regular expressions and sentence scoring find each field and keep the quote it came from; it never invents a value.
  * How is text taken out of a PDF, Word file or transcript? - backend/app/drafts/extract_text.py -> extract_text(). Picks the reader by file type, normalizes the text and refuses files that are too large or unreadable.
  * How are meeting captions (VTT/SRT) cleaned? - backend/app/ai/transcripts.py -> clean_transcript(). Drops cue numbers and timings, merges split captions and keeps one line per speaker turn.
  * Screen: create from upload - src/screens/CreateFromUpload.tsx -> CreateFromUpload(). Upload or paste notes, review the extracted draft, then create the project.

C. Steps 2-3 - AI intake and scope review
  * Where is an intake run started? - backend/app/api/v1/intake.py -> create_run(). Queues a run over the pasted text plus every uploaded document whose text was read.
  * Who does the work in the background? - backend/app/jobs/intake.py -> IntakeRunner._suggest(). Asks Claude for scope items; falls back to the rules (model 'rules', no tokens) when there is no key or Claude fails.
  * How is the AI stopped from inventing scope? - backend/app/ai/intake_llm.py -> suggestions_from_model(). Every item must quote the notes; items whose quote isn't really in the notes are dropped (see `grounded_suggestion` in ai/evidence.py).
  * How does the rules fallback find scope items? - backend/app/ai/intake_rules.py -> extract_by_rules(). Reads headings, bullets and keyword-matched sentences and labels each as a requirement, deliverable, risk and so on.
  * How is prompt injection prevented? - backend/app/ai/prompting.py -> as_data(). User text is escaped and wrapped in a data block, so it can't close or open prompt tags.
  * Where are documents uploaded (up to 100 MB)? - backend/app/api/v1/documents.py -> upload_document(). Streams the file, reads its text in a worker thread and stores it for the next intake run.
  * Why can't I go to the WBS with items still pending? - src/screens/scope/gate.ts -> scopeGate(). Pending scope items block step 4 until each one is accepted or rejected.
  * Screens: intake and scope review - src/screens/ScopeReview.tsx -> ScopeReview(). Accept, edit or reject each extracted item with its quote; AIProjectIntake.tsx runs the analysis.

D. Step 4 - Work breakdown structure (WBS)
  * Where is the WBS generated? - backend/app/jobs/ai_jobs.py -> AiJobRunner._generate(). Claude proposes deliverables and work packages from the accepted scope; without a key a template plan is used, then owners are suggested.
  * What is the no-AI WBS template? - backend/app/ai/wbs_generate.py -> template_plan(). One deliverable per deliverable scope item, each with generic work packages and durations.
  * What do the free WBS checks verify? - backend/app/ai/wbs_validate.py -> check_structure(). Tree shape, names, durations, owners and whether the critical path fits before the deadline.
  * How is the critical path length computed? - backend/app/ai/wbs_validate.py -> critical_path_days(). Longest chain of work packages through the dependency graph; returns None if the links form a cycle.
  * Where are the live checks served? - backend/app/api/v1/wbs.py -> wbs_checks(). Runs the deterministic checks on current data on every visit, so warnings are never stale.
  * Where are AI duration estimates confirmed? - backend/app/api/v1/wbs.py -> confirm_estimates(). The optimizer refuses to run until AI-estimated durations are confirmed by a person.
  * How does the database keep the WBS tree valid? - supabase/migrations/20261114000100_cross_project_links.sql -> private.validate_wbs_parent(). Trigger: a node's parent must be in the same project and the tree can't loop.
  * Screen: WBS builder - src/screens/WBSBuilder.tsx -> WBSBuilder(). Tree table with inline editing (components/WbsTable.tsx), generate and validate buttons.

E. Step 5 - Team, skills and constraints
  * Where is a person added to the team? - backend/app/api/v1/team.py -> add_team_member(). Employee (company rate, or the $85/h default) or Contractor (rate required); reuses the organization's person of that name.
  * How are required skills linked to work packages? - backend/app/optimization/skill_links.py -> link_skills(). Uses each package's tagged skills (minus Optional ones) and links Required skills nobody tagged by keyword, so the solver knows who qualifies.
  * Where are the budget, deadline and milestones saved? - backend/app/api/v1/planning.py -> put_constraints(). Each limit has a policy: 'Must hold' (hard) or 'Can flex' (soft, penalized).
  * Where are dependencies created? - backend/app/api/v1/planning.py -> create_dependency(). FS/SS/FF/SF links with lag between two work packages of the same project.
  * How does the database stop cross-project links? - supabase/migrations/20261114000100_cross_project_links.sql -> private.validate_dependency(). Trigger: both work packages must belong to the same project (fixes a QA-found hole).
  * Screen: constraints - src/screens/Constraints.tsx -> Constraints(). Budget, deadline, milestones, team hours and dependencies with their policies.

F. Step 6 - Optimization (Google OR-Tools CP-SAT)
  * What is checked before a run may start? - backend/app/optimization/input_sheet.py -> build_sheet(). Builds the 'Check the inputs' sheet in screen order and lists what still blocks the run (no team, unconfirmed estimates, unanswered questions).
  * Where is a run queued? - backend/app/api/v1/optimization.py -> create_run(). Freezes every input into a snapshot so the run is reproducible; returns 422 with what is missing.
  * How is a second run at the same time prevented? - backend/app/repositories/optimization.py -> OptimizationRepository.lock_run_creation(). A Postgres advisory lock per project, held until the transaction ends, so a double-click can't start two runs.
  * How does the app know the inputs changed since the plan? - backend/app/optimization/inputs.py -> inputs_hash(). SHA-256 of exactly what the solver uses (not today's date or other projects' bookings); compared with the applied plan's hash.
  * Who runs the solver? - backend/app/jobs/optimizer.py -> OptimizationRunner._run(). Claims a queued run, solves its frozen input on a worker thread, prices remedies if needed and stores the report.
  * Where is the mathematical model (variables, constraints, objective)? - backend/app/optimization/solver.py -> solve(). The module docstring has the full formulation: one assignment boolean per task and person, duration set by the person, capacity, skills, dependencies, deadline and budget; objective in cents.
  * Where are the CP-SAT variables and constraints added? - backend/app/optimization/builder.py -> ModelBuilder.build(). Adds every task, the workload, dependencies, makespan, deadlines and budget, then minimizes the sum of costs and penalties.
  * How does skill level change speed? - backend/app/optimization/speed.py -> pace_percent(). 10% faster per level above the minimum (at most 30%); 25% slower per level below.
  * How are part-time hours and overtime limited? - backend/app/optimization/load.py -> flex_capacity_tenths(). 'Can flex' allows up to 25% over contracted hours; `task_mode` stretches a task for part-timers.
  * How is a plan's cost computed? - backend/app/optimization/costing.py -> plan_cost(). Each task's remaining hours at the person's pace times their rate, plus the overtime premium; all in cents.
  * What is the 'before optimization' baseline? - backend/app/optimization/baseline.py -> baseline_plan(). Current owners at WBS durations, as early as dependencies allow; finished work keeps its dates.
  * How is useless overtime removed? - backend/app/optimization/polish.py -> without_overtime(). Re-solves without overtime and keeps that plan if it achieves the same dates and cost.
  * How is an impossible plan explained? - backend/app/optimization/blockers.py -> explain_infeasibility(). Puts each hard constraint group behind an assumption and extracts every independent conflict, worded in plain English.
  * Where are the priced options when the date slips? - backend/app/optimization/remedies.py -> price_remedies(). Re-solves relaxed variants (bring in specialists, allow overtime, move the deadline, or a combination) and offers the ones that help, with their cost.
  * Which date does a re-plan aim for? - backend/app/optimization/model.py -> target_of(). The plan in force's finish date for a re-plan, otherwise the project's must-finish-by date.
  * Where are KPIs and 'why did this move' reasons built? - backend/app/optimization/explain.py -> build_report(). Turns the solution into KPI cards, rows to store and per-task reasons (skill gap, over-allocation, cost, waiting).
  * Screen: optimization results - src/screens/OptimizationResults.tsx -> OptimizationResults(). Inputs sheet, solver status, Gantt (optimization/PlanGantt.tsx) and the 'keep the date' options.

G. Plan v1 - apply and export
  * Where is a run applied as the next plan version? - backend/app/api/v1/plan.py -> apply_run(). Refuses with 409 if the inputs changed since the run (stale plan); otherwise calls the SQL function.
  * What does applying a plan write? - supabase/migrations/20261113000600_apply_allocation_hours.sql -> public.apply_optimization_run(). One transaction: task owners and dates, booked hours per week, and the new plan version.
  * Which plan is in force? - backend/app/repositories/optimization.py -> OptimizationRepository.applied_run(). The run applied last, with the inputs hash it was approved with.
  * Where are the PDF and MS Project exports? - backend/app/export/pdf.py -> render_pdf(). Landscape PDF of the schedule; export/msproject.py `render_msproject` writes MSPDI XML.
  * Browser side of applying a plan - src/lib/queries/optimization.ts -> useApplyRun(). TanStack Query mutation that applies the run and refreshes the project's data.

H. Step 7 - Changes and versions (Plan v1 → v2)
  * Where is a mid-project change recorded? - backend/app/api/v1/changes.py -> create_change(). Stores the change (notes, edits or team changes) and finds what it affects.
  * How are changes found in meeting notes without AI? - backend/app/changes/detect.py -> detect(). Rules read budget, deadline, durations, hours, people and new scope from each sentence, keep its verbatim quote, and turn anything unclear into a question.
  * How does Claude read the notes? - backend/app/changes/llm.py -> ChangeDetector.detect(). Structured output checked against the notes; falls back to the rules if Claude fails.
  * Which questions does a change ask? - backend/app/changes/questions.py -> build_questions(). Values that conflict with ones you confirmed are asked, never silently overwritten.
  * How do answers become a re-plan? - backend/app/changes/derive.py -> derive_overrides(). Turns the change and its answers into what-if overrides applied to the frozen inputs.
  * How is Plan vN+1 compared with Plan vN? - backend/app/changes/compare.py -> build_comparison(). Per work package: old and new dates, the shift, and why it moved.
  * Where is a change approved? - backend/app/api/v1/changes.py -> approve_change(). The re-plan becomes the next plan version and the change's values become the project's inputs.
  * Why doesn't an approved plan look outdated right away? - backend/app/repositories/changes.py -> ChangeRepository.record_inputs_in_force(). Saves the inputs hash at approval, so the plan in force matches its own inputs.
  * Screen: changes and versions - src/screens/ChangesVersions.tsx -> ChangesVersions(). Report a change, answer questions, re-plan, compare (changes/PlanComparison.tsx) and approve.

I. Dashboard and planning assistant
  * How is the per-project dashboard built? - backend/app/domain/overview.py -> build_overview(). Combines status, budget, milestones, delivery health, risks and the next step from stored facts.
  * Where are the KPI cards drawn? - src/components/DashboardCards.tsx -> DashboardKpis(). Budget, completion, utilization and plan cards from the overview response.
  * Screen: dashboard - src/screens/Dashboard.tsx -> Dashboard(). Project picker, KPI cards, health, risks, notifications and AI findings.
  * Where is the planning assistant? - backend/app/api/v1/assistant.py -> ask_assistant(). Answers questions about the current page and project using its live context (ai/assistant.py).

J. Tests and tooling
  * Backend unit and API tests (pytest) - backend/tests. Run with `cd backend && uv run pytest` (521 tests); folders mirror the app packages.
  * Database security tests (pgTAP) - supabase/tests/database. Check RLS, deletes, applying a run and uploads directly in Postgres.
  * End-to-end API scenarios - tests/e2e/api/run_api_suite.py -> main(). About 240 business scenarios across all 7 steps against a running API, without Claude tokens.
  * Demo data seed (Jane Doe's projects) - scripts/seed_demo/seed_demo.py -> main(). Creates the demo account and five projects through the public API, up to Plan v2.

      ScenarioLog.status() - Checks an HTTP status (and optionally a phrase in the error detail).
      ScenarioLog.counts() - How many outcomes have each verdict.
      ScenarioLog.summary_line() - `**PASS** 236 · **FAIL** 1 · …`, the line a reader looks at first.
      ScenarioLog.area_summary() - A table of verdict counts per area, in the order the areas ran.
      ScenarioLog.write() - Rewrites the report: totals, notes, counts per area, then one table per area.
